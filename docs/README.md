## 3. 关键架构决定

1. 以企业管理闭环为主线，而不是以 OA 功能菜单为主线。
2. 首期采用模块化单体和统一 PostgreSQL，边界稳定后再拆服务。
3. 网页与三大协同平台共享同一领域层、权限层、Agent 层和审计层。
4. 外部平台只是交互渠道和数据源，不是系统事实源。
5. Agent 的有效权限等于用户权限、工具权限、数据范围和场景策略的交集。
6. 所有高风险动作必须进入持久化工作流并经过人工确认。
7. 文档、模型输出和外部事件均视为不可信输入。
8. 首个纵向闭环为“项目风险发现 → 管理决策 → 行动落实 → 追踪复盘”。
9. Agent 确认只排队持久化任务，业务副作用由可租约、可恢复的 Worker 执行。
10. 生产界面和 Readiness 只陈述可由权威数据与运行证据证明的事实。
11. 主工作对话是产品第一入口；模型基于完整权限化上下文自主选择 Skill/Tool，确定性代码只执行安全与状态约束。

## 4. 需求追踪规则

- 产品需求使用 `PR-*`。
- 管理规则使用 `MR-*`。
- 架构约束使用 `AR-*`。
- 安全要求使用 `SR-*`。
- 连接器要求使用 `IR-*`。
- 验收标准使用 `AC-*`。
- 持久化运行契约使用 `DR-*`。
- 测试用例必须引用至少一个需求或约束 ID。

## 5. 文档变更规则

- 影响业务语义、权限、外部协议和验收口径的修改必须先改文档，再改代码。
- 破坏性变更必须新增 ADR，并说明迁移和回滚方式。
- 文档中不得保存 Secret、Token、用户原始对话或未脱敏企业数据。
