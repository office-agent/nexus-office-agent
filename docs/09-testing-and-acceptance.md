# 09 测试与验收方案

## 1. 测试原则

- 以需求 ID、风险和业务状态机组织测试，不以代码覆盖率代替验收。
- 所有外部平台先通过本地契约模拟器，再进入真实沙箱/测试企业。
- 模型测试允许非确定性，但工具参数、权限和副作用必须确定。
- 测试数据全部虚构或脱敏，禁止生产消息进入自动测试。

## 2. 测试分层

### 2.1 单元测试

- 领域状态机、RACI、权限组合、风险评分。
- 外部事件规范化和幂等键。
- Agent 风险分类、确认策略和工具 Schema。
- LLM 原生 Tool Call、权限化工具可见性、任务状态机、证据门禁和承接版本竞争。
- 加密/验签封装使用官方测试向量，不记录真实 Secret。

目标：核心领域与安全策略分支覆盖 ≥ 90%。

### 2.2 集成测试

- PostgreSQL 约束、事务、Outbox/Inbox。
- 租户过滤和字段权限。
- 工作流重试、补偿、并发确认。
- RAG 权限过滤与索引失效。
- 模型接口使用受控 Fake Model 和少量真实连通探针。
- 主会话唯一性、Agent run 幂等写回、SSE 游标恢复和 PostgreSQL compare-and-set 承接。

### 2.3 连接器契约测试

每个平台测试：

- URL/Stream 鉴权。
- 有效事件、无效签名、错误密文、重放、重复事件。
- Token 过期和刷新竞争。
- 限流、429/平台错误、超时和网络中断。
- 消息/卡片发送、更新、重复写和回执。
- 组织全量同步、增量事件、删除/离职和对账。

连接器必须可在无真实凭据时通过协议 Fixture 完成 CI；真实企业测试作为发布 Gate。

企业接入验收还必须覆盖三类旅程：

1. 未配置凭据：返回 `blocked` 和明确前置代码，不伪造通过。
2. 错误凭据或平台级错误码：返回 `failed`，即使 HTTP 状态为 200。
3. 重复事件/重复确认：只能产生一次副作用；缺回执的未知结果不得自动重试。

真实测试通知的自动测试只使用 Fake Gateway；仅在受控测试企业中，由管理员通过两阶段确认执行真实外发。证据必须同时包含方案 ID、方案哈希、审计 trace ID、回执摘要和平台侧核对结果。

### 2.4 E2E

核心旅程：

1. 用户登录网页并查看授权范围内项目。
2. 创建目标和项目，分配 Owner。
3. 外部事件触发项目风险。
4. Agent 给出带引用分析和处置提案。
5. 经理从网页或平台卡片确认。
6. 系统创建行动项并通知责任人。
7. 责任人完成，系统更新风险和项目状态。
8. 管理者查看完整审计和复盘。

### 2.5 安全测试

- 跨租户、IDOR、角色提升、字段越权。
- CSRF、XSS、SSRF、SQL 注入、开放重定向。
- Prompt Injection、数据外泄、工具越权和确认绕过。
- Webhook 伪造、重放、压缩炸弹和超大消息。
- Secret/PII 日志扫描和前端 Bundle 扫描。

### 2.6 韧性测试

- 数据库短暂不可用。
- Redis 丢失缓存。
- 模型供应商超时或限流。
- 单个平台完全不可用。
- Worker 崩溃和重复消费。
- 长连接断线重连。
- Outbox 积压和死信恢复。
- 租约过期回收、旧令牌拒绝和 Worker 优雅关闭。
- Agent 工具业务写入后、任务完成前崩溃的幂等重放。
- Outbox 发布回执后、完成标记前崩溃的幂等重放。

## 3. Agent 评测集

评测集至少包含：正常问答、无权限问题、信息不足、冲突证据、过期文档、恶意文档指令、高风险动作、重复确认、对象版本冲突和平台故障。

评分：

- groundedness / citation correctness
- permission correctness
- action policy correctness
- tool argument correctness
- refusal correctness
- task completion
- latency / cost

## 4. 验收标准

| ID | 标准 | 证据 |
|---|---|---|
| AC-001 | 网页与三平台共享同一业务状态 | 四渠道 E2E 结果与数据库状态 |
| AC-002 | 核心管理闭环端到端可运行 | 核心旅程录像/日志/审计 ID |
| AC-003 | 跨租户与越权访问全部拒绝 | 安全测试报告 |
| AC-004 | R3/R4 未确认不可执行 | 策略和 E2E 测试 |
| AC-005 | 重复事件不产生重复副作用 | 连接器契约测试 |
| AC-006 | 平台/模型失败可降级恢复 | 韧性测试报告 |
| AC-007 | Agent 重要结论有权限正确的引用 | 评测报告 |
| AC-008 | Secret 不进入源码、日志、前端和测试产物 | 扫描报告 |
| AC-009 | 关键性能指标达到架构目标 | 压测报告 |
| AC-010 | 备份、恢复、回滚和密钥轮换完成演练 | 演练记录 |
| AC-011 | 网页与企业微信共享 M12 管理智能事实，渠道确认重鉴权且幂等 | API/PostgreSQL/企业微信 Fixture/浏览器/真实测试企业证据 |
| AC-012 | 主对话、任务发布/分派/承接/推进共享持久事实，业务路由由模型经 Skill/Tool 完成 | LLM Tool Call、API、PostgreSQL CAS/RLS/审计、SSE 与桌面/移动浏览器证据 |

## 5. 发布 Gate

1. 设计 Gate：文档、数据模型、权限矩阵、威胁模型通过。
2. 开发 Gate：类型、Lint、单元、集成和契约测试通过。
3. 安全 Gate：无未处置 Critical/High，越权与 Secret 检查通过。
4. 沙箱 Gate：三平台测试企业端到端通过。
5. 试点 Gate：真实团队完成至少两个管理闭环，无数据事故。
6. 生产 Gate：监控、告警、备份、回滚和应急预案就绪。

## 6. 不允许的完成声明

- 只有页面演示不能声称模块完成。
- 只有 Mock 不能声称平台集成完成。
- 只有 API 200 不能证明业务副作用成功。
- 没有跨租户测试不能声称多租户安全。
- 没有引用和权限评测不能声称企业 RAG 完成。
- 没有真实测试企业凭据时必须明确标记三平台“代码完成、外部验收待执行”。
- 确认请求内同步执行副作用、无真实 Worker 消费或只有环境变量声明的能力，不得称为持久化运行完成。
- 生产界面包含虚构企业、人员、任务或 Agent 结论时，不得称为真实业务可用。

## 7. 自动需求追踪 Gate

- 所有 `*.test.ts` 必须通过机器可读行为证据映射引用至少一个规范需求或运行契约 ID；测试标题或首行引用只用于导航，不单独构成证据。
- `tests/requirement-traceability.test.ts` 从本文档集合提取规范 ID，并验证实现位置、实际执行的测试、失败路径和新鲜结果；M11 同时追踪 `DR-001` 至 `DR-014`。
- `AC-001` 与 `AC-010` 即使已有本地部分证据，也必须保持外部 Gate 状态；真实 IdP、三平台企业、灾备轮换和团队试点证据见 [需求追踪矩阵](./15-requirement-traceability.md)。
- Agent 旅程测试中的“pass”只表示预期契约成立。例如预期 `blocked` 且实际 `blocked` 是失败关闭契约通过，不代表外部 IdP 或平台验收通过。
- 持久化运行的行为旅程和完成边界见 [16 持久化执行与崩溃恢复设计](./16-durable-runtime.md)。
